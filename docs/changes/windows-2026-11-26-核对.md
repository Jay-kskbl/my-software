## 2. 发现的问题

### Bug 1：Windows 上数据库停掉时，后端接口会一直挂着不返回（要修）

- **现象**（17.6 第 3a 步）：后端开着、PostgreSQL 停掉，刷新文件页，`/api/auth/me` 超过 90 秒都没有返回，既不是 503 也没有报错。同一时刻 `/health` 4.8 秒就正确报告数据库不可用，因为健康检查设了超时。
- **原因**：`backend/app/db/session.py` 的 `make_engine()` 没有给数据库连接设超时。执行方实测，Windows 上 psycopg 3.3.9 连一个被拒绝的本机端口，不会立刻失败，而是一直等到超时（设 10 秒就等 10 秒）；不设超时就一直等。macOS、Linux 上同样的情况会立刻报“连接被拒绝”，所以本机测不出来。两个 Worker 早在 T24k 就设了超时，不受影响。
- **影响**：数据库出问题时，网页上所有需要数据库的操作都卡住，用户看不到“数据库不可用”的提示，违反 GLOBAL §12（要能区分没有结果和服务故障）。
- **建议修法**：`make_engine()` 传入连接超时（例如新配置 `DATABASE_CONNECT_TIMEOUT_SECONDS`，默认 5 秒），超时后按现有逻辑返回 503。不改表结构、接口。

### Bug 2：`test_database_address_is_hidden` 在 Windows 上失败（测试写法问题）

- 这个测试（T24ba）连 `127.0.0.1:1`，指望错误文字里带地址。Windows 上得到的是 `connection timeout expired`，不带地址，前置检查就失败了。被测的脱敏函数没有问题。
- **建议修法**：测试改用一段写死的、带地址的错误文字，不依赖真实网络。

### 其他

- **`git_dirty` 总是 true**：实验记录用 `git status --porcelain` 判断工作区是否干净，未跟踪的文件也算在内。Windows 上一直有 `output/` 下的未跟踪目录，所以每次都记成不干净，这个标志失去了意义。建议只看已跟踪文件（加 `--untracked-files=no`）。
- **17.14 的结论**（写进 T30 部署说明和论文）：一个 OCR Worker 约占 2.0–2.2 GB 提交内存；16 GB 机器同时运行 PostgreSQL、OpenSearch、CLIP 时，最多开 3 个；N=3 的吞吐约是 N=1 的 1.75 倍。
